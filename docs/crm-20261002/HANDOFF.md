## Runtime and cross-team contracts

Use `crmRuntime(root).operations.list()` and `.run(name, input, verifiedPrincipal)` for Jarvis and other trusted internal callers. The HTTP buttons use the same registry through `POST /__crm/ops`. `by` is derived from the verified principal. Ownership is responsibility, never an access filter. Remote server writes require the existing confirmed-founder session and that caller's page token.

`crmRuntime(root).automations.accept(event, verifiedPrincipal)` accepts an already-authenticated source occurrence. It uses the existing durable JobService, CRM transactional receipts and semantic/event dedupe. It starts no timer and sends nothing. Won transitions invoke this adapter now. Incoming enquiry/reply/meeting and scheduled proposal/renewal occurrences need the owning services to deliver their authenticated occurrences; enabling a rule is not proof that its source is connected.

`configureCrmIntegrations(root, { verifyAgent, verifyCommunicationEvidence })` installs trusted server readers and returns an unregister function. No browser configuration endpoint exists. The agent verifier receives attribution, principal and target reference; validate the persisted job, identity and recorded `subjects` before approving. The communication verifier receives provider evidence, principal and target reference; bind the provider message to that record. Default behaviour is fail-closed. The current baseline's Jobs type has no general `subjects` field: Claude owns that addition and Jarvis dispatch wiring under `AGENTS-CRM-CONTRACTS.md`. Do not approve an agent or provider event from its JSON claims alone.

Saved results remain `artifact:<jobId>[/file]` references to existing identity-gated routes. CRM events contain only `{ref, change, at}`, shared with the verified founders; they contain no field values. Memory is context and cannot overwrite CRM records.

Finance links are existing invoice-reference documents whose HTTPS URL exactly matches a saved Stripe invoice in the existing Finance database. Reads are read-only, never sync providers, infer payment from Won, fuzzy-match a name/amount or create a ledger. Missing/ambiguous/malformed/stale snapshots are explicit. Non-Stripe invoices can remain linked documents; their payment status is unknown until the existing Finance source exposes verified evidence.
