# Load performance, 27 Sep 2026

Why AgenticOS "takes forever to load sometimes", what changed, and the numbers.
Stopped on the owner's instruction; the numbers below are all that were collected.

## Causes found (biggest first)

1. **Restart storm.** vite.config.ts imports every server plugin, so all ~420 files under
   `scripts/**` are Vite config dependencies. Any save closes the HTTP server and rebuilds the
   dev server. With agents editing `scripts/**` this happened about once a minute (11 restarts
   in 9 minutes observed). Each restart killed in-flight chat turns and agent tasks, made the
   open tab fully reload, and threw away every transformed module: the first response after a
   restart took 14-23 s (23.6 s measured on live 8081).
2. **Three page bodies in every page.** `agents.hermes.tsx` (11k lines), `dashboard.tsx` (4k) and
   `setup.tsx` (3k) exported components used by other pages. TanStack never code-splits a
   route file's exports, so the eager route tree loaded all three plus their dependencies
   (model-intelligence, intelligence-portal, the 1.4 MB power-design graph JSON) on every route.
3. **Heavy overlays in the shell.** `FloatingOracle` (voice companion, wake word, chat input,
   oracle visuals) and `AccountsHub` (connections panel, audience charts, recharts) were static
   imports of `__root.tsx`: ~3 MB of modules hydrated before any page was interactive.
4. **Uncached model catalog.** `GET /__operator/models` spawns `codex app-server` and
   `claude auth status` every call; the Business page asks three times at once (1.5-4 s each).

Not a cause: Vite dependency pre-bundling is stable (no re-optimisation reloads seen); the
lovable-tagger plugin is inert outside a Lovable sandbox; warm SSR is fast (<0.3 s).

and file watching off. "Before" and "after" are snapshot copies of the same tree (before = my
changes reverted) with an empty workspace, so both see identical data. Medians of 4 runs. The
machine was loaded by other agents, so server-start times varied 3-23 s between identical runs.

## os-shell (27 Sep 2026, ~20:30 Sydney, branch `w2/os-shell-20260927`)

**Method.** Same machine, same method for both sides, run back to back. Before = a `git archive` of
the base commit `735256d`; after = this branch at `dda27f0` + the Today change below. Each ran as a
quiet copy on 127.0.0.1:4301 (`AGENTIC_OS_NO_BACKGROUND=1`, plus `ARGENTIC_PREVIEW=1` so Vite's
dependency cache is private to the copy and never touches the live server's). Each copy was warmed
once (every page visited), then restarted for the cold-start number. Headless Chromium
(playwright-core 1.62), GET requests and sidebar clicks only; medians of 3 fresh-context loads.
"Page data" = when the first response of each of the page's own endpoints had arrived (e.g. the six
`/__workspace/*` panels for Today/Workspace, `/__receptionist`, `/__ai_usage`). "API before data" =
local `/__*` requests the browser had started before that moment (the queue the page's data waited
in). JS = script bytes transferred in the first 4 s (dev server, unbundled modules).

What changed:

1. The shell's polling overlays (Jarvis HUD, live agent panel, background jobs, chat/voice dock)
   mount once the page's own React Query fetches have been quiet for 250 ms (cap 4 s), instead of
   at first idle; a trigger event (Voice, HUD toggle, agent feed) still mounts them at once and is
   replayed. Their ~14 requests now start after the page's data, not in front of it
   (`src/components/shell/late.tsx`).
2. The accounts hub (ConnectionsPanel → recharts) loads only when "Connect account" is pressed.
3. Each destination reads only what it renders: Work asks for 4 panel sources (not the receptionist
   and email panels it doesn't show); Today asks for all six because it shows a signal from each;
   `/__operator/models` (spawns the Codex and Claude CLIs on a cold cache) is read by System only.
4. A batched `GET /__workspace` for Today was built and measured, then dropped: it made every card
   wait for the slowest source (the public site checks, 1.1–2.6 s when their 5-minute cache
   expires). One small request per source, with the overlays out of the way, shows the fast cards
   first and finishes no later.

Still open:

- **Memory revisit, 1.6–2.0 s.** Returning to `/memory` blocks the main thread for 1.2–1.5 s before
  the URL even changes (one long task: the memory page mounting its 3D view synchronously once its
  chunk is cached). Same on the base commit (1.94 s measured with the same script), so not a shell
  regression. Fix belongs in `src/components/operator/memory-workspace.tsx`: mount
  `MemoryUniverse` after first paint (`useDeferredValue`/`startTransition` or an idle callback).
- The overlays still fire ~14 requests together once the page settles (`maxApiInflight` 10 both
  sides); staggering the chat/voice dock a second later would flatten that.
- `OperatorJobs` and the chat/voice dock each request their endpoints twice on mount (effect re-runs
  on first data); owners: `src/components/operator-jobs.tsx`, `src/components/floating-oracle.tsx`.
